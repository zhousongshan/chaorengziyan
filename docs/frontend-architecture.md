# 前端架构基线

## 第一阶段范围

第一阶段只实现单张商品图的普通模式闭环。Agent、Session、资产库和视频页面保留路由边界，
但在后端领域接口完成前不使用前端假数据伪造业务结果。

当前已经完成登录到可交付结果的真实数据链路：恢复最近项目、读取可用生图模型、上传一张商品主体图、
提交需求 AI、回答多条澄清问题、确认结构化需求、创建异步生图任务、展示生成结果并完成主体一致性质检。
质检需要用户补充信息时，页面会保存回答并恢复工作流；只有质检通过的生成结果才开放原图入口。

## 路由

- `/login`：开发态登录入口。
- `/create`：智能创作 Agent 管理页；列表、筛选、分页和自建 Agent CRUD 均来自 API。
- `/create/image`：普通模式生图工作台；把 `requirementRunId` 和 `taskId` 写入 URL，刷新时从 API 恢复。
- `/tasks/[taskId]`：后续承载可刷新的生成和质检任务。

开发态登录通过同源 Route Handler 设置 HttpOnly Cookie，仅在
非生产环境且 `AUTHORIZATION_DRIVER` 未设置或为 `development` 时开放。它不是生产认证实现，
生产构建会自动禁用；正式身份服务接入后替换该适配器。

## 第二阶段 Agent 管理

Agent 由 PostgreSQL 和 `/api/v1/agents` API 统一管理。`owner_user_id` 为空的记录是全局系统 Agent，
所有用户可读取和复制，但不能重命名或删除；自建 Agent 带用户归属，查询、改名和删除均在 Repository
条件中校验归属。复制只复制名称、简介、类型、模式和 Agent 设定，不复制会话、记忆、素材或生成历史。

从 `/create` 进入工作台时使用 URL 中的 `agentId` 读取 Agent 名称、简介和初始设定。工作台创建会话后，
`agentInstruction` 会随消息写入不可变的会话状态快照，后续刷新以会话快照为准，不持续读取可变的
Agent 记录。删除 Agent 因此不会改变或删除已经存在的会话和生成结果。Agent 设定仍低于用户本轮明确
指令、商品事实和系统主体保护边界。

当前只开放生图 Agent。视频 Agent 的类型展示保留，但创建入口禁用，避免在视频后端尚未实现时产生
无法执行的数据。

## 状态边界

- PostgreSQL/API：任务和资产的唯一事实来源。
- TanStack Query：服务端资源、请求状态、缓存和重新拉取。
- Zustand：未提交的需求草稿、上传队列和临时面板状态，不保存任务最终状态。
- React Hook Form：单个页面表单的校验、错误和提交生命周期。
- URL：保存 `requirementRunId`、`taskId` 等可恢复标识；刷新后从 API 恢复服务端结果。

异步状态必须遵守 `docs/async-state-consistency.md`。对“当前会话是否仍有后台任务”这一问题，活跃任务 REST 接口是权威源：查询成功后必须接受其非空或空结果，历史任务缓存只能在该查询尚未成功时保守兜底。SSE 和历史缓存不得推翻权威空结果。按钮忙碌状态、工作流阶段和历史展示可以分别派生，但必须共享相同的权威优先级。

## 普通模式数据流

1. 页面从 API 恢复当前用户最近使用的项目；没有项目时创建默认项目。
2. 页面读取后端模型目录，并根据选中模型限制图片数量和比例。
3. 第一次提交时先上传商品主体图，再把稳定的 `assetId` 交给需求 API。
4. 需求 AI 需要澄清时，前端逐条收集答案；后端创建带父子关系的新需求运行，原记录保持不变。
5. 需求整理成功后只展示结构化确认结果，并把运行 ID 写入 URL；刷新页面后通过该 ID 恢复。
6. 用户确认后，前端提交需求运行 ID 和稳定的幂等键；后端读取不可变需求并创建生图任务。
7. 前端通过 SSE 接收状态通知，同时保留 REST 定时拉取作为断线和丢事件补偿。
8. 任务成功后，前端从媒体资产 API 展示已经保存到自有存储的生成图，并读取每张输出对应的质检记录。
9. 质检通过前只提供预览。前端通过独立的质检 SSE 接收状态通知，并以 REST 查询作为断线补偿。
10. 需求有歧义时逐条收集一次用户回答；回答按原问题顺序提交并作为不可变记录保存，然后恢复需求 AI
    重整和第二次质检。商品原图证据不足时不接受文字补充，必须引导用户更换清晰商品图。
11. 第二次检查仍失败时停止该结果，展示具体变化、原图观察、生成图观察和失败原因，并提示用户修改需求
    或更换商品图。模型超时、限流等执行错误单独显示，不占用两次业务检查额度。

需求 API 失败后保留已经上传的 `assetId`，再次提交不会重复上传同一份商品图。用户替换本地商品图时，
草稿状态会清除旧 `assetId`，下一次提交再上传新图。

生图任务的幂等键以需求运行 ID 为维度保存在浏览器 `sessionStorage`。同一页面重复点击或创建响应丢失时，
后端数据库唯一约束会返回原任务而不是重复创建；用户在明确失败后点击“重新生成”才会生成新的幂等键。

生图指令在任务创建时生成并冻结，保存指令版本。Worker 只能读取该快照，不能根据后续部署的新 Prompt
重新解释已经进入队列的任务。指令明确包含“主体默认全部保持”和“仅用户明确授权项允许变化”。

## 契约与实时状态

所有 REST 响应通过 `@chaoren/contracts` 的 Zod Schema 解析。SSE 只做状态通知，收到事件后让
TanStack Query 更新或重新拉取；断线期间由 REST 查询补偿，不能把 SSE 当作状态存储。

当前 SSE 端点以 PostgreSQL 任务状态为来源，每 1.5 秒检测变化并在终态关闭连接。适用于第一阶段规模；
当并发连接量明显增长时，可以保持前端契约不变，将服务端实现替换为 Redis Pub/Sub 或数据库 Outbox
事件分发。

生成任务和主体质检使用两个独立 SSE：前者只通知媒体生成状态，后者聚合该任务下所有输出的质检状态。
聚合状态包含等待、运行、待用户补充、全部通过、部分通过、拒绝、执行失败和取消。页面不能用“生图成功”
代替“可交付成功”。

商品主体图、参考图和生成图必须使用不同字段和组件。第一阶段商品主体图最多一张。

商品主体默认保持身份、形状、结构、部件、颜色、材质、图案、Logo 和包装不变；只有用户明确要求时，
需求 AI 才能把对应特征列入允许变化项。背景、构图、灯光和创意风格不能被解释为修改商品主体。
