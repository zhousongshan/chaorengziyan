# 异步任务状态一致性与恢复规范

## 1. 文档目的

本文沉淀 2026-08-12 “后端任务已经完成，前端仍永久显示生成中”问题的事实、排查过程、根因、修复方式和长期开发要求。

本文适用于所有跨前端、API、数据库、队列和 Worker 的异步流程，包括但不限于：

- 会话需求理解；
- 图片生成；
- 主体质检与自动修复；
- 视频生成；
- 上传、转码、导出和批处理；
- 任何使用轮询、SSE、缓存、父子任务或后台恢复的功能。

目标不是修复某一个按钮，而是保证系统在并发、缓存滞后、事件丢失、进程退出和页面刷新后，最终都能恢复到数据库表达的真实业务状态。

## 2. 本次问题

### 2.1 用户现象

- 会话中已经展示最终生成图片。
- 助手消息表示任务已经完成。
- 输入框仍被禁用，提交按钮一直显示“生成中”。
- 刷新页面后问题仍可能存在。
- 后端已经没有真正需要执行的生成或质检工作。

### 2.2 涉及的状态

本次链路同时存在多个状态，它们回答的问题不同：

| 状态              | 回答的问题                         | 可能的值                                           |
| ----------------- | ---------------------------------- | -------------------------------------------------- |
| 生成任务状态      | 生图供应商执行是否结束             | `queued/running/succeeded/failed/cancelled`        |
| 输出质检状态      | 生成候选是否完成检查并可交付       | `queued/running/completed/...`                     |
| 工作流汇总状态    | 本轮最终交付结果是什么             | `running/succeeded/partially_succeeded/failed/...` |
| Creation Run 状态 | 整个后台执行生命周期是否仍占用会话 | `queued/running/cancelling/terminal/cancelled`     |
| 活跃任务接口      | 当前会话是否仍有后台工作流         | `{ task }` 或 `{ task: null }`                     |
| 前端历史查询缓存  | 页面上一次读取到的任务快照         | 可能滞后                                           |
| SSE 事件          | 某个时间点发生了状态变化           | 可能延迟、丢失或断开                               |

“图片生成成功”和“整个工作流已经结束”不是同一个事实。前端历史缓存、SSE 事件和 URL 也都不是最终业务事实来源。

## 3. 排查过程与证据

### 3.1 从用户可见状态反推锁定条件

页面结果已经展示，但按钮仍显示“生成中”，说明图片展示条件和编辑器忙碌条件来自不同状态源。代码检查确认编辑器同时受到以下条件影响：

- 会话 `processingMessageId`；
- 活跃任务接口返回值；
- 历史任务列表中的 `workflowStatus/status`；
- 当前任务推导出的 UI stage；
- 本地 mutation 是否 pending。

### 3.2 发现轮询竞态

Worker 的正常完成顺序为：

1. 将最后一个生成单元或质检记录写为终态；
2. 根据所有子任务状态，将 `creation_runs.status` 收口为 `terminal`。

这两个动作不是同一个数据库事务，因此存在一个短暂窗口：

```text
输出和质检已经终态
  -> 序列化出的 workflowStatus 已是 succeeded
  -> creation_run 仍是 running
  -> 活跃接口仍返回 task
```

旧前端看到 `workflowStatus=succeeded` 后停止轮询，但又因为活跃接口缓存中仍有非空 `task` 而保持忙碌。最后一次查询如果正好落在这个窗口，页面就永久卡住。

### 3.3 发现第二个缓存回退问题

修正轮询后，真实页面仍能复现。只读检查得到：

- 会话 `processingMessageId=null`；
- `/image-generations/active` 返回 `{ task: null }`；
- 页面仍显示“生成中”。

原因是前端在权威活跃接口返回空后，又回退到不会同步刷新的历史任务列表。历史列表仍保留旧 `running` 快照，随后 UI stage 也从该旧快照推导为 `generation_running`，页面再次被锁住。

### 3.4 发现崩溃恢复缺口

即使正常竞态得到修复，如果 Worker 恰好在“子任务写终态”和“Creation Run 收口”之间退出，数据库可能永久保留：

```text
creation_run = running
所有生成单元 = 终态
所有质检 = 终态
没有任何可恢复队列工作
```

原恢复逻辑只重新投递未完成单元和质检，不会修复这种已经没有可执行子任务的孤儿 run。它会导致：

- 活跃接口永久返回任务；
- 前端永久显示生成中；
- 同一会话的新任务被“已有活跃任务”规则永久拒绝。

## 4. 根因

### 4.1 直接原因

1. 前端使用派生的 `workflowStatus` 决定是否停止“活跃任务接口”的轮询。
2. 权威活跃接口已经返回 `null` 后，旧历史缓存仍能覆盖该结论。
3. UI stage 和提交按钮分别重复推导忙碌状态，没有共享相同的权威优先级。
4. Creation Run 收口与最后一个子任务终态写入存在跨事务崩溃窗口。
5. Worker 恢复只恢复“未完成工作”，没有恢复“父状态未收口但子工作已全部完成”的情况。

### 4.2 本质原因

系统没有为每一个业务问题明确唯一的权威状态源，并把不同层级、不同时间点的状态当成了可以互相替代的布尔值。

具体表现为：

- 把“输出成功”误当成“工作流不再活跃”；
- 把“缓存里曾经运行”误当成“数据库现在仍在运行”；
- 把“SSE/轮询停止”误当成“最终状态已可靠同步”；
- 只设计正常状态转换，没有设计跨事务中断后的状态收敛；
- 测试只覆盖各层状态一致的正常数据，没有构造权威状态和缓存互相矛盾的组合。

## 5. 修复结论

### 5.1 前端

- 活跃任务接口只要仍返回任务，就继续轮询，不能因返回任务的派生状态已经成功而停止。
- 只有活跃任务接口明确返回 `task: null`，才能证明该会话当前没有活跃 Creation Run。
- 活跃接口请求成功后，它对“当前是否仍有后台工作”具有最高优先级。
- 历史任务列表只能在活跃接口尚未成功时作为保守回退，不能推翻权威空结果。
- 活跃接口由非空变为空时，主动失效历史任务查询，使展示快照也尽快收敛。
- 提交按钮和 UI stage 必须使用相同的权威优先级；不能各自独立拼接一套忙碌条件。

### 5.2 Worker

- Worker 启动时和周期恢复时执行孤儿 run 收口。
- 对仍为 `queued/running` 的 Creation Run，只有同时满足以下条件才可改为 `terminal`：
  - 不存在 `queued/running` 的生成单元；
  - 不存在 `queued/running` 的主体质检；
  - 不存在仍需执行的旧版无单元任务。
- 收口必须由数据库条件更新完成，避免先读后写时出现新的并发竞态。
- 有真实运行中单元或质检时不得提前收口。

### 5.3 最终验证

- 原问题会话的活跃接口返回 `task: null`。
- 同一页面按钮恢复为“发送”，输入框可编辑。
- 无输入时按钮保持正常禁用，不再显示假忙碌。
- 浏览器控制台无错误。
- 真实 PostgreSQL 和 Redis 集成测试验证了“仍有质检时不收口、最后质检完成后可恢复收口”。

## 6. 长期状态设计要求

### 6.1 先定义问题，再定义权威源

新增或修改异步状态前，必须填写以下表格。不同问题允许有不同权威源，但每个问题只能有一个最终权威源。

| 必答问题                       | 示例答案                         |
| ------------------------------ | -------------------------------- |
| 当前子任务是否执行完成？       | 生成单元或质检记录               |
| 当前结果是否可交付？           | 输出级 `deliverableAsset/status` |
| 当前工作流最终结论是什么？     | 由所有输出推导的 workflow status |
| 当前会话是否仍被后台任务占用？ | Creation Run / 活跃任务接口      |
| 页面缓存能否推翻数据库结论？   | 不能                             |
| SSE 能否作为最终事实？         | 不能，只能通知重新读取           |

禁止使用一个笼统的 `isProcessing` 在不同模块中代表不同问题，也禁止仅因为字段名称相似就互相替代。

### 6.2 明确状态层级

父状态和子状态必须分别建模：

```text
Creation Run
  -> Generation Task
    -> Generation Unit
      -> Provider Attempt
      -> Subject Consistency Check
        -> Repair Generation
```

必须明确：

- 哪个层级负责资源占用；
- 哪个层级负责最终业务结论；
- 父状态如何由子状态收口；
- 子状态终态后父状态是否仍可能活跃；
- 部分成功、取消和自动修复如何传播；
- 后加入的修复任务是否属于原 Creation Run。

### 6.3 缓存和实时事件规则

- PostgreSQL 是持久业务事实来源。
- REST 查询用于读取可恢复状态。
- SSE、WebSocket 和队列事件只用于通知变化，不持有最终状态。
- 前端缓存是快照，必须有明确失效和重新拉取条件。
- 权威查询成功返回“空”也是有效业务结果，不能被旧非空缓存覆盖。
- 查询失败与权威空结果必须区分：失败时可以保守回退，成功为空时必须接受空结果。
- 轮询的停止条件必须来自该轮询接口自身表达的完成语义，不能借用另一个层级的派生状态。

### 6.4 跨事务与崩溃恢复规则

对任何“先写子状态、再写父状态”的流程，设计时必须回答：

1. 进程在两次写入之间退出会留下什么数据？
2. 重启后谁负责发现并修复？
3. 恢复操作是否幂等？
4. 恢复是否可能把仍在运行的任务提前结束？
5. 永久遗留状态是否会阻止用户后续操作？

优先使用同一事务原子提交。确实不能放入同一事务时，必须提供周期性 reconciliation，并使用数据库条件更新保证并发安全。不能只依赖 `finally`、队列 completed 回调或进程优雅退出。

### 6.5 UI 忙碌状态规则

- 忙碌状态必须由集中函数或明确状态机推导，不能在多个组件中重复拼布尔表达式。
- “任务是否活跃”“当前展示阶段”“按钮是否可提交”可以是三个派生结果，但必须共享相同权威数据和优先级。
- 页面刷新、SSE 断开、后台恢复、历史缓存滞后后，UI 必须最终收敛。
- 用户可见的成功结果与忙碌按钮不能长期矛盾。
- 权威数据暂不可用时应展示可恢复的服务状态或错误，不得永久静默禁用。

## 7. 强制测试方法

### 7.1 状态转换单元测试

每个状态机至少覆盖：

- 每条合法转换；
- 每条非法转换；
- 所有终态不可重新执行；
- 取消、部分成功和自动修复；
- 重复事件和幂等重放。

### 7.2 不一致组合测试

不能只测试“所有层都 running”或“所有层都 succeeded”。必须主动构造矛盾状态：

| 权威活跃接口 | 历史缓存    | 子任务/质检   | 页面或系统预期           |
| ------------ | ----------- | ------------- | ------------------------ |
| 返回 task    | `running`   | 运行中        | 显示处理中并继续轮询     |
| 返回 task    | `succeeded` | 父 run 未收口 | 继续轮询，不提前解锁     |
| 返回 `null`  | `running`   | 全部终态      | 立即解锁并刷新历史缓存   |
| 返回 `null`  | `succeeded` | 全部终态      | 显示完成                 |
| 查询失败     | `running`   | 未知          | 保守回退，不伪造完成     |
| 查询失败     | `succeeded` | 未知          | 显示查询错误或可恢复状态 |

每次线上或人工发现的状态 Bug，必须先写出能够复现矛盾组合的最小回归测试。

### 7.3 生产仓储集成测试

以下行为必须使用真实 PostgreSQL 仓储验证，不能只使用内存实现：

- 父子状态收口；
- 活跃任务唯一性；
- 并发创建和幂等键；
- 部分成功；
- 自动修复任务属于原 run；
- Worker 重启恢复；
- 孤儿 run reconciliation；
- 迟到结果、取消和终态保护。

涉及队列恢复时同时使用真实 Redis/BullMQ。测试使用随机 ID、独立队列名并在结束时清理数据。

### 7.4 崩溃窗口测试

对每一个跨事务边界，至少模拟一次中断：

1. 写入最后一个子任务终态；
2. 不执行正常父状态收口；
3. 模拟 Worker 重启或直接运行恢复器；
4. 断言父状态最终收口；
5. 再执行一次恢复器，断言幂等；
6. 保留一个运行中子任务重复测试，断言不得提前收口。

### 7.5 浏览器端到端验收

状态类改动完成后，至少验证：

- 真实页面展示最终结果；
- 活跃接口最终返回空；
- 输入框恢复可用；
- 按钮从处理中恢复为正常命令；
- 无输入时只因输入规则禁用，不因旧任务禁用；
- 刷新后状态一致；
- SSE 断开或禁用后 REST 轮询仍可收敛；
- 浏览器控制台无运行时错误。

端到端测试不能只断言页面出现图片，还要同时断言后续操作能力已经恢复。

## 8. 开发与评审检查清单

任何异步任务、状态、轮询、SSE、缓存或 Worker 改动，在实现和评审时必须回答：

1. 每个状态分别回答什么业务问题？
2. 对每个问题，唯一权威源是什么？
3. 哪些数据只是缓存、通知或派生展示？
4. 权威空结果会不会被旧缓存覆盖？
5. 查询失败和查询成功但为空是否被正确区分？
6. 轮询为什么停止，停止依据属于同一层级吗？
7. 父子状态在哪一步收口？是否存在跨事务窗口？
8. Worker 在任意 `await` 后退出，重启时如何收敛？
9. 恢复操作是否幂等、并发安全且不会提前终止？
10. 当前状态是否会永久阻止用户提交下一次任务？
11. 是否测试了至少一个权威状态与缓存冲突的组合？
12. 是否用生产 PostgreSQL 仓储验证关键状态机？
13. 是否验证刷新、SSE 断开和进程重启？
14. 是否验证最终业务结果与按钮、输入框等操作能力一致？

任何一项没有可靠答案，都不能把功能视为完成。

## 9. 结论

本次问题的本质不是“前端没有及时刷新”，而是系统缺少跨层状态权威、优先级和崩溃收敛约束。

长期规则是：

- 不同层级的状态不能因为都叫成功或运行中就互相替代；
- 每个业务问题必须有唯一权威源；
- 缓存和事件只能加速展示，不能推翻权威事实；
- 正常完成路径和崩溃恢复路径必须收敛到同一终态；
- 测试必须主动制造状态不一致，而不只验证理想流程；
- 页面最终状态不仅要“显示成功”，还要恢复用户下一步操作能力。

以后再出现“后台完成但页面仍处理中”“结果可见但不能继续操作”“重启后任务永久占用”等现象，应首先按本文检查状态层级、权威优先级、缓存回退和父状态收口，而不是先增加超时或强制刷新掩盖问题。

## 10. 强制验证命令与可观测性

涉及异步状态的改动在交付前必须使用 Node 24 执行：

```bash
pnpm verify:release
```

该命令包含：

- `pnpm verify`：格式、Lint、类型检查、普通测试和生产构建；
- `pnpm test:integration`：API 与 Worker 的真实 PostgreSQL/Redis 集成测试；
- `pnpm test:e2e:state`：桌面和移动端异步状态 Playwright 回归。

集成测试必须使用独立测试数据库，不能与开发数据库或生产数据库相同。状态 E2E 必须覆盖刷新和 SSE 丢失，并同时断言结果展示与下一步操作能力。

Worker 恢复必须输出结构化事件：

- `orphaned_creation_runs_finalized`：记录收口数量、Run ID、最大存续时间和收口原因；
- `stale_active_creation_runs_detected`：记录超过 15 分钟的活跃 Run、状态、最大存续时间和无变化时间。

同一组超龄 Run 只在集合发生变化或间隔 15 分钟后再次告警，避免周期恢复每 30 秒重复刷屏。超龄检查只用于诊断和告警，不能作为自动收口条件。是否收口仍必须由“没有运行中单元、质检和旧版任务”的数据库条件决定。
