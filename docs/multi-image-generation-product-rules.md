# 多图片独立生图产品规则

## 1. 文档目的

本文定义普通模式下，多张图片输入、自然语言需求理解、生成数量决策、执行计划、生图、主体一致性质检、自动修复、部分失败和最终交付的完整产品规则。

本文是产品和工程共同遵守的业务基线。实现不得依赖模糊推断补齐关键血缘，也不得因为单个输出失败而丢弃其他已经成功的输出。

## 2. 核心原则

1. 用户本轮明确表达的自然语言要求优先于页面默认控件。
2. 用户没有明确表达时，页面控件是本轮执行参数的默认来源。
3. 多张输入图片之间的关系必须由需求 AI 结合本轮文字和图片判断，程序不得预设它们一定是同一商品的多角度图。
4. 每个输出必须拥有独立、冻结、可追溯的执行计划和商品原图血缘。
5. 主体一致性质检按输出执行，只使用该输出实际对应的商品原图，不使用本轮其他无关原图。
6. 主体一致性质检只判断商品主体是否发生未授权变化，不判断背景、构图、审美或用户其他编辑要求是否完成。
7. 单个输出生图异常时，只重试该输出一次。仍失败则保留其他成功结果，并向用户说明该输出真实、可行动的业务原因。
8. 生图成功不等于可交付成功。需要主体质检的输出只有通过质检后才能成为交付结果。
9. 所有数量、图片血缘、允许变化、任务尝试和结果状态必须持久化，不能依靠页面内存或 Worker 临时推断。

## 3. 关键概念

### 3.1 资产角色

- `product_source`：商品事实来源，可作为主体质检原图。
- `user_reference`：只提供场景、构图、风格等参考，不能作为商品事实。
- `edit_base`：本轮需要继续修改的画面。
- `generated_result`：历史生成结果。
- `selected_result`：用户明确选中的历史生成结果。
- `rejected_result`：已经被用户或系统拒绝的历史结果。

### 3.2 执行用途

- `edit_target`：本执行单元直接编辑的画面。
- `subject_fact`：用于保持商品身份和细节的事实图片。
- `composition_member`：需要被组合进同一输出的商品或对象。
- `style_reference`：只提供视觉风格参考。
- `layout_cell`：拼图或版式中的一个画面单元。

资产角色和执行用途是两个独立维度，不能互相覆盖。例如，一张 `product_source` 可以在某个执行单元中同时是 `edit_target`，但它仍然是该输出的商品质检原图。

### 3.3 输出单元

一个输出单元代表一个最终独立文件。每个输出单元至少冻结以下信息：

- `unitId`
- 输出位置和所属分组
- 输出形式
- 本单元指令
- 本单元使用的源图片及用途
- 本单元对应的商品原图 ID
- 是否需要主体质检
- 生图尝试记录
- 主体质检记录
- 最终可交付资产 ID

## 4. 完整处理链路

### 4.1 上传与输入准备

1. 用户上传 1 至 4 张商品图，可选上传 1 张参考图。
2. 每张图片上传时校验文件大小、真实图片格式、解码能力和资产归属。
3. 上传成功后获得稳定的 `assetId`。后续流程只使用 `assetId`，不依赖浏览器临时文件。
4. 商品图、参考图、水印和编辑基图使用不同字段保存，不能因为 UI 展示位置相同而混用。
5. 用户移除或替换图片后，后续请求不得继续携带已经移除的资产。

#### 上传资产精确去重

- 只有用户上传资产参与去重；模型生成资产和交付资产始终保留独立 `assetId` 与生成血缘。
- 去重身份只使用原始上传字节的 SHA-256，文件名不参与身份判断，也不使用感知哈希或视觉相似度。
- 去重范围是同一用户、同一项目、同一媒体类型。范围内 SHA-256 完全相同时复用已有 `assetId`，不重复写入文件和资产记录。
- SHA-256 不同必须创建新 `assetId`，即使文件名相同或图片看起来非常相似；SHA-256 相同则视为同一份原始文件，即使上传时间和文件名不同。
- `assetId` 对应的文件内容不可变。不得为了去重覆盖已有 `assetId` 的文件，否则会破坏历史会话、任务和血缘。
- 数据库唯一约束负责收口并发上传；并发失败方只清理自己新写入且未落库的存储对象，再返回数据库中的标准资产。

### 4.2 需求理解

需求 AI 接收：

- 本轮用户文字；
- 页面控件；
- 当前会话有效状态；
- 本轮和必要历史图片；
- 每张图片的稳定句柄、资产角色和关系说明；
- 模型技术上限。

需求 AI 必须判断：

- 用户是否要求立即生成；
- 多张图片是分别处理、同商品多角度、多商品组合、风格参考还是拼图；
- 用户明确允许修改哪些商品特征；
- 是否存在阻塞执行的真实歧义；
- 每个输出使用哪些图片；
- 最终独立文件数量。

只有执行结果会发生实质差异且无法从用户表达确定时才向用户澄清。不得为程序可以确定的技术规则向用户提问。

### 4.3 数量决策规则

数量按以下优先级确定：

1. 本轮文字中的明确输出语义；
2. 本轮页面图片数量控件；
3. 会话中仍有效的上一轮数量；
4. 系统默认值 1。

以下都属于明确输出语义：

- “生成 4 张”；
- “每张原图各生成 1 张”，且本轮有 4 张目标原图；
- “给每个商品分别出一张”；
- “只要 2 个方案”；
- “再来一张”。

以下不视为可直接覆盖控件的确定数量：

- “多生成几张”；
- “大概三四张”；
- “多给几个方案”。

当文字明确数量和控件冲突时，文字优先，不向用户重复确认。助手回复和生成前状态必须明确展示最终解析数量。

示例：控件选择 3，用户写“4 张完整且独立的商品主图”，最终数量为 4。

最终执行计划所有分组的 `outputCount` 总和必须等于解析后的最终数量。程序不得静默截断、补足或改变数量。

如果明确数量超过模型或产品上限：

- 不得静默改成上限；
- 不得直接开始部分生成；
- 应说明当前最多支持的数量，并要求用户调整后再执行。

### 4.4 多图关系与执行计划

#### 每张原图分别处理

有 N 张目标原图时建立 N 个分组，每组只引用对应原图，默认每组输出 1 张独立文件。

```text
原图 1 -> 输出单元 1
原图 2 -> 输出单元 2
原图 3 -> 输出单元 3
原图 4 -> 输出单元 4
```

不得把其他原图加入当前单元，也不得把 N 张结果拼成一个画布。

#### 同一商品多角度

同一输出可以引用该商品的多张角度或细节图。所有被确认属于同一商品且与本次输出有关的原图共同构成商品事实来源。

#### 多商品组合

同一输出可以引用多个不同商品。执行计划必须保留每个商品实体和它各自的原图集合，不能把不同商品描述成同一商品的多角度。

#### 参考图

参考图只能以 `style_reference`、`layout_cell` 等非商品事实用途进入计划。参考图不能进入主体一致性质检原图集合。

参考图的视觉分析、迁移决策、执行冻结和真实场景验收统一遵守 `docs/reference-image-product-rules.md`。图片已经绑定或传给模型只代表输入链路成功，不代表参考图功能已经完成。

#### 修改历史生成结果

历史生成结果可以作为 `edit_target`，但不能自动成为商品事实。系统必须沿结果血缘找到最初的 `product_source`，并将这些原图作为主体质检依据。

### 4.5 执行前冻结

需求确定后冻结：

- 用户原始文字；
- 最终结构化需求；
- 最终数量；
- 执行计划；
- 每个输出的源图片；
- 每个输出的商品质检原图；
- 模型和渲染参数；
- Prompt 版本；
- 执行计划哈希。

Worker 必须读取冻结快照，不能使用部署后的新 Prompt 重新解释已经入队的任务。

每个输出单元的模型指令必须根据本单元实际收到的图片生成。例如本单元只收到一张编辑目标时，指令不得写“输入图片 1 至 4 是同一商品”。

### 4.6 生图执行与单元重试

每个输出单元独立执行，初始最多调用一次；发生生图执行异常时，只对失败单元自动重试一次。

```text
单元初次执行
  -> 成功：进入结果保存
  -> 失败：记录 attempt 1
       -> 自动重试同一单元
            -> 成功：进入结果保存
            -> 失败：记录 attempt 2，单元终止
```

重试必须保持以下内容不变：

- 原始需求快照；
- 本单元源图片；
- 本单元商品原图血缘；
- 模型选择；
- 比例、质量和输出设置；
- 本单元业务指令。

重试不得重新执行已经成功的其他单元。每次供应商提交使用可追踪的尝试编号和幂等键。某次超时请求之后才返回结果时，只允许一个有效结果原子落库，其他迟到结果必须忽略或清理。

以下属于生图执行异常：

- 供应商网络失败；
- 超时；
- 限流；
- 供应商 5xx；
- 供应商返回无效图片；
- 结果下载失败；
- 单元要求一张但供应商没有返回一张有效图片。

模型未配置、模型不支持、源图片不存在或权限错误属于确定性错误，可以直接终止，不做无意义重试。

### 4.7 结果保存与任务汇总

每个成功输出先独立验证并保存。单个输出失败不得回滚其他已成功输出。

用户可见汇总状态：

- `succeeded`：全部输出成功并完成各自要求的质检和交付；
- `partially_succeeded`：至少一个输出可交付，同时至少一个输出最终失败或被质检拒绝；
- `failed`：没有任何输出可交付；
- `running`：仍有输出处于生图、重试、质检、修复或交付处理中。

汇总结果必须展示：

- 请求数量；
- 成功数量；
- 处理中数量；
- 失败数量；
- 每个失败输出的位置、稳定错误码和用户可理解原因。

### 4.8 按输出绑定主体质检原图

是否需要主体质检由每个输出单元独立决定：

- 使用商品原图事实的输出需要质检；
- 编辑商品图的输出需要质检；
- 修改历史商品生成结果的输出需要质检，并沿血缘回溯到原商品图；
- 只生成背景、装饰或不含商品事实的输出不需要主体质检。

质检原图选择规则：

1. 每张原图分别处理：输出 i 只绑定原图 i。
2. 同一商品多角度：绑定该商品与当前输出有关的全部原图。
3. 多商品组合：绑定输出中每个商品各自的原图，且保留商品实体分组。
4. 单张原图内包含多个商品：该原图是这些商品的共同可见事实来源，用户提供的尺寸、名称和关系同时进入确认需求。
5. 参考图、风格图、布局图不得作为商品质检原图。
6. 生成结果不得替代原商品图成为事实来源。

每个需要质检的成功输出必须创建且只创建一条当前工作流版本的主体质检记录。任务级 `subjectConsistencyRequired` 只能作为汇总字段，不能替代输出级质检状态。

如果系统无法确定某个输出应绑定哪些商品原图，应在生图前要求需求 AI 澄清或判定计划无效，不能在生图后把本轮全部商品图笼统交给质检模型。

### 4.9 主体一致性质检边界

主体质检只比较原商品图与生成结果中可见、可比较的商品特征，包括：

- 商品身份；
- 形状和几何关系；
- 结构和部件；
- 固有颜色；
- 材质和纹理；
- 图案、文字和 Logo；
- 包装特征；
- 需求明确涉及的姿态、朝向、表情或相对尺寸。

主体质检允许：

- 合理裁切、遮挡和缩放；
- 视角、焦距和透视变化；
- 用户在 `allowedChanges` 中明确授权的主体变化。

主体质检不负责判断：

- 背景是否符合要求；
- 构图是否高级；
- 风格是否美观；
- 红框、道具或其他非主体编辑是否完成；
- 营销效果和审美质量。

这是明确的产品边界，不应被当作质检遗漏。用户可以通过会话继续要求修改不满意的创作结果。

### 4.10 质检失败后的自动修复

主体质检业务不通过和生图执行异常是两个不同流程。

首次主体质检结果：

- `passed`：进入交付处理；
- `source_unusable`：停止该输出，要求更换清晰商品原图；
- `failed`：记录具体未授权变化，进入一次自动主体修复；
- `execution_failed`：按质检执行异常规则处理，不占用两轮业务质检额度。

自动主体修复只能：

- 增加针对性的 `mustKeep`；
- 增加针对性的 `mustAvoid`；
- 使用当前输出对应的原商品图重新生成该输出。

自动修复不得：

- 放宽用户原意；
- 新增主体修改授权；
- 修改数量、比例、场景、背景、构图或风格；
- 修复其他已经通过的输出。

修复图生成后进行第二轮主体质检：

- 通过：以修复图作为交付候选；
- 仍不通过：停止该输出，向用户说明具体差异并建议调整需求或更换原图；
- 原图证据不足：要求更换原图；
- 执行异常：说明质检或修复服务异常。

一个输出最多两轮主体业务质检，不进行无限自动修复。

### 4.11 交付处理

不需要主体质检的输出在生成图片验证通过后进入交付处理。需要主体质检的输出只有在质检通过后进入交付处理。

交付处理包括：

- 输出格式转换；
- 水印处理；
- 最终文件验证；
- 保存交付资产；
- 建立生成资产到交付资产的血缘。

被主体质检拒绝的图片可以作为过程预览和审计证据，但不能提供“下载原图”或标记为可交付结果。

部分成功时，已经通过完整链路的结果应立即可查看和下载，不等待其他已经终止的失败输出。

### 4.12 会话恢复与实时状态

- PostgreSQL 是任务、单元、尝试、质检和资产的唯一事实来源。
- URL 保存可恢复的会话和任务 ID。
- SSE 只通知状态变化，不保存业务状态。
- SSE 断开时使用 REST 轮询恢复。
- Worker 重启后只恢复未完成单元，不重新执行已经成功或终止的单元。
- 会话中的旧 `editBaseAssetId` 只能在用户继续修改同一结果时沿用。用户发起全新商品图任务时必须显式清除，不能污染新计划。

## 5. 异常处理规则

| 阶段     | 异常                         | 自动处理                     | 最终处理与用户提示                           |
| -------- | ---------------------------- | ---------------------------- | -------------------------------------------- |
| 上传     | 文件过大                     | 不重试                       | 说明大小上限，要求压缩或更换图片             |
| 上传     | 声明格式不支持               | 不重试                       | 说明仅支持 JPEG、PNG、WebP                   |
| 上传     | 文件无法真实解码或 MIME 不符 | 不重试                       | 说明图片损坏或格式不正确，要求更换           |
| 上传     | 资产不属于当前用户或项目     | 不重试                       | 拒绝访问，不泄露资产是否属于其他用户         |
| 需求理解 | 用户需求存在阻塞歧义         | 不生图                       | 提出最少且具体的澄清问题                     |
| 需求理解 | 文字数量超过上限             | 不截断                       | 说明当前上限，要求用户调整                   |
| 需求理解 | AI 网络失败或超时            | 按服务策略重试               | 仍失败则说明需求理解服务暂时不可用           |
| 需求理解 | AI JSON 外壳不合法           | 只做一次格式修复             | 仍无效则记录校验问题并停止，不改变用户语义   |
| 执行计划 | 引用了不存在的图片句柄       | 格式修复不得虚构图片         | 计划无效，停止生成并记录具体字段             |
| 执行计划 | 输出数量与最终数量不一致     | 不静默修改                   | 计划无效，重新整理或停止                     |
| 执行计划 | 需要质检但无法确定对应原图   | 不允许入队                   | 要求澄清图片关系或重新整理计划               |
| 生图单元 | 网络、超时、限流、5xx        | 只重试当前单元一次           | 仍失败则标记该输出失败，说明实际类别         |
| 生图单元 | 返回空文件、非图片或无法解码 | 只重试当前单元一次           | 仍失败则说明生图服务返回无效图片             |
| 生图单元 | 模型未配置或不支持           | 不重试                       | 说明所选模型当前不可用，要求更换或联系管理员 |
| 生图单元 | 源图片丢失或归属不一致       | 不重试                       | 说明源图片不可用，要求重新上传或重新创建任务 |
| 结果保存 | 存储写入失败                 | 清理本次未入库文件后重试一次 | 仍失败则说明结果保存失败，其他输出不回滚     |
| 主体质检 | 原图证据不足                 | 不自动修复                   | 要求更换更清晰或更完整的对应商品原图         |
| 主体质检 | 首轮发现未授权变化           | 只修复当前输出一次           | 收紧主体保护要求并进入第二轮质检             |
| 主体质检 | 第二轮仍不一致               | 不再修复                     | 展示具体差异，建议调整需求或更换原图         |
| 主体质检 | AI 网络、超时、限流、5xx     | 只重试本次质检执行一次       | 仍失败则标记质检执行失败，不伪装成主体不一致 |
| 主体质检 | AI 返回格式错误              | 只做一次格式修复             | 仍无效则标记质检执行失败                     |
| 修复生图 | 供应商执行异常               | 只重试当前修复输出一次       | 仍失败则说明主体修复生成失败                 |
| 交付     | 格式转换或水印失败           | 只重试交付处理一次           | 仍失败则保留过程图，说明最终文件处理失败     |
| 实时状态 | SSE 断开                     | 自动切换 REST 轮询           | 页面继续显示真实数据库状态，不提示任务失败   |
| 会话     | 版本冲突                     | 不覆盖新状态                 | 提示页面已在其他窗口更新并刷新恢复           |
| 队列     | 投递失败                     | 任务写入失败状态或进入补投   | 提示任务服务暂时不可用，不重复创建业务任务   |

### 5.1 用户错误信息要求

用户看到的原因必须真实对应已知业务类别，例如：

- “第 3 张图片生成等待超时，系统自动重试一次后仍未完成。”
- “第 2 张图片的商品主体两次检查仍不一致，鸡腿鸡的颜色和翅膀结构发生了未授权变化。”
- “第 4 张图片无法完成主体检查，因为对应商品原图不够清晰。”
- “第 1 张图片已经生成，但最终 PNG 转换失败。”

不得把已知超时、限流、无效图片、原图损坏等原因全部模糊成“系统繁忙”。

同时，真实原因不等于直接暴露供应商原始响应。以下内容只进入内部日志：

- API Key；
- 内部 URL；
- 代理和队列名称；
- 数据库错误详情；
- 供应商原始响应正文；
- 堆栈；
- 其他用户或项目标识。

每个错误记录应包含稳定错误码、安全用户文案、内部诊断信息和关联尝试 ID。

## 6. 典型场景验收

### 6.1 四张商品图分别优化

输入：

- 上传 4 张商品图；
- 控件数量选择 3；
- 用户明确要求每张图分别优化并输出 4 张独立图片；
- 每张图包含菜花鸡和鸡腿鸡；
- 用户提供两者尺寸关系，允许互换位置，要求去除红框，其他保持不变。

预期：

1. 文字明确数量优先，最终数量为 4。
2. 创建 4 个独立输出单元，每个单元只引用对应的一张原图。
3. 每个单元的模型指令只描述自己实际收到的图片。
4. 每个输出都标记需要主体质检。
5. 输出 1 只使用原图 1 质检，输出 2 只使用原图 2 质检，以此类推。
6. 菜花鸡和鸡腿鸡的身份、外观和用户给出的相对尺寸关系进入确认需求。
7. 位置互换属于明确允许的变化；其他未授权商品特征保持不变。
8. 主体质检不负责判断红框是否去除，这是当前产品边界。
9. 4 个输出分别通过质检后，交付 4 个独立文件，不生成拼图。

### 6.2 一个输出生图两次失败

```text
输出 1：成功 -> 质检通过 -> 可交付
输出 2：成功 -> 质检通过 -> 可交付
输出 3：初次超时 -> 自动重试 -> 再次超时 -> 最终失败
输出 4：成功 -> 质检通过 -> 可交付
```

预期：

- 任务显示 `partially_succeeded`；
- 交付输出 1、2、4；
- 不重新生成 1、2、4；
- 用户看到“第 3 张生成等待超时，自动重试一次后仍未完成”；
- 用户可以继续使用三个成功结果，也可以在后续会话中明确要求重新生成第 3 张。

### 6.3 一个输出主体首次质检失败

```text
输出 2 初次生成成功
  -> 对比原图 2
  -> 发现未授权结构变化
  -> 只为输出 2 收紧 mustKeep / mustAvoid
  -> 只重新生成输出 2
  -> 第二轮仍只对比原图 2
```

其他已经通过的输出不重新生成、不重新质检。

### 6.4 用户继续修改历史结果后发起新任务

用户先修改历史输出 2，随后上传全新的 4 张商品图并要求分别生成。

预期：

- 旧输出 2 不再作为新任务的编辑基图；
- 新任务只使用本轮 4 张商品图；
- 旧编辑基图仍保留在会话历史中，但不进入新执行计划。

## 7. 必须补齐的验收测试

1. 控件为 3、文字明确为 4，最终计划和任务均为 4。
2. 文字没有数量时，使用控件数量。
3. 文字数量超过上限时不静默截断。
4. 四张原图分别处理时，四个单元各自只收到一张对应原图。
5. 每个单元生成的提示词只描述本单元实际图片。
6. `product_source + edit_target` 仍保留商品质检原图身份。
7. 四张独立输出成功后创建四条质检记录，并分别绑定原图 1 至 4。
8. 参考图永远不会进入主体质检原图集合。
9. 历史生成结果作为编辑目标时，质检能够回溯原商品图。
10. 单元首次失败后只重试该单元一次。
11. 单元第二次失败后，其他成功输出不回滚、不重跑。
12. 部分成功状态返回正确数量、位置和错误原因。
13. 主体首次失败只修复对应输出，第二轮仍使用相同商品原图血缘。
14. 新商品任务能够清除旧 `editBaseAssetId`。
15. Worker 重启后不重复执行已经成功的单元。
16. SSE 断开后 REST 轮询能恢复最终状态。

## 8. 实现落地顺序

1. 将资产角色、执行用途和质检原图血缘拆成独立字段并持久化。
2. 将生图指令改为按输出单元的实际源图片生成。
3. 将主体质检创建条件改为输出级规则，保证一个需要质检的输出对应一条质检记录。
4. 固化“明确文字数量优先，否则使用控件”的数量解析与校验规则。
5. 增加 `clearEditBase` 或等价的新任务语义，阻止旧编辑基图污染新任务。
6. 为每个输出建立最多两次生图尝试，并支持只重试失败单元。
7. 增加 `partially_succeeded` 用户态和逐输出错误展示。
8. 补齐上传解码校验、恢复幂等和上述端到端测试。
