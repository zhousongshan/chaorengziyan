# 工程错误知识：把开放的 AI 语义输出误当成封闭数据结构

## 记录信息

- 记录日期：2026-08-06
- 事件模块：普通模式需求整理、会话记忆、多模态图片理解
- 事件级别：阻断核心流程
- 当前状态：根因已确认；输出契约改造待实施
- 适用范围：需求 AI、质检 AI、Repair AI、图片记忆、创意规划以及后续所有模型结构化输出

## 一、事情是什么

用户上传商品图并点击“整理需求”后，前端持续收到 HTTP 502，无法进入生图阶段。

排查过程中先后出现过两类表面错误：

1. 显式 HTTP 代理处理较大的图片请求时断开连接，产生 `fetch failed / ECONNRESET`。
2. 网络恢复后，上游模型能够成功读取图片并返回合法 JSON，但后端仍然返回 502。

对第二类错误使用同一份用户输入和同一张商品图进行只读复现后，确认模型返回内容存在以下结构差异：

- `assetMemories[0]` 没有返回 `creativeFacts`。
- 模型把 `result` 放进了 `assetMemories[0]`。
- JSON 根节点没有程序要求的 `result`。
- `assetMemories[0]` 出现程序 Schema 未允许的额外字段。

模型已经完成了图片理解和需求整理，返回内容也是合法 JSON；但程序使用严格、封闭的 Schema 拒绝了整份结果，随后把具体校验错误统一包装为 `Bad Gateway Exception`，用户最终只能看到没有解释能力的 502。

## 二、直接原因

当前多模态需求接口要求模型一次返回一个复杂且完全固定的对象：

```text
assistantReply
+ changedFields
+ assetMemories
+ result
+ result.finalRequirement
+ conflictDecisions
```

程序使用严格 Schema 校验：

- 必填字段缺失即失败。
- 字段层级稍有变化即失败。
- 出现未声明字段即失败。
- 辅助字段不完整也会阻断核心需求结果。

同时，模型调用只使用了 `response_format: json_object`。该配置只能保证输出是合法 JSON，不能保证字段位置、必填字段和嵌套层级完全符合程序 Schema。

当前会话版需求整理又没有格式规范化或格式修复步骤，因此任何轻微结构偏差都会直接变成 502。

## 三、根本原因

根本原因不是少写了一条校验规则，而是使用了错误的建模思想：

> 把开放、不确定、持续演化的 AI 语义输出，当成了传统后端中封闭、可穷举、完全确定的数据结构。

这一错误来自以下错误假设：

### 错误假设 1：字段齐全就等于需求完整

程序可以检查字段是否存在，但无法判断用户需求在语义上是否完整。

`scene`、`style`、`mustKeep` 等字段都有值，不代表真正理解了用户；部分字段为 `null`，也不代表需求不可执行。

需求是否充分，应由需求 AI 结合用户输入、图片和会话上下文判断；不确定时由需求 AI 返回澄清问题。

### 错误假设 2：程序可以判断主体策略是否合理

程序可以确认：

- `defaultAction` 是否能够被执行。
- `allowedChanges` 是否可以被解析。
- 数据是否超过客观技术限制。

程序无法独立确认：

- 某项主体变化是否真的是用户原意。
- 用户的描述是否构成明确授权。
- 某个商品是否存在未预定义的新特征。
- 某项变化是否属于完成创意目标不可避免的最小范围。

这些属于语义理解，不属于确定性程序校验。

### 错误假设 3：提前定义的字段集合可以覆盖未来需求

电商商品特征、图片事实和创意信息是开放集合。未来一定会出现当前没有想到的部件、图案、结构、表情、附件、包装和业务属性。

如果程序将“未预定义”解释为“非法”，系统会不断因为新增合理信息而失败。

### 错误假设 4：越严格越安全

严格校验只适用于程序确实掌握真相的领域，例如：

- 用户、项目和资产归属
- UUID 和任务血缘
- 权限
- 状态机转换
- 幂等约束
- 文件大小和 MIME 类型
- 供应商明确公布的技术限制
- 数据库事务和唯一索引

严格校验不适合直接判断开放语义，例如：

- 用户意图是否完整
- 创意描述是否充分
- 商品特征是否穷尽
- 主体变化是否合理
- 图片语义事实是否只能使用预设字段表达

把两类数据使用同一种严格程度处理，不会提高安全性，只会提高误杀率。

### 错误假设 5：辅助能力失败可以阻断核心能力

`assetMemories` 是会话图片记忆的辅助产物，`creativeFacts` 又是其中的辅助字段。

即使图片记忆不完整，只要最终需求可用，核心需求整理也不应该失败。当前设计把所有结果耦合成一个不可分割的成功条件，导致一个非核心字段缺失就让整个任务不可用。

## 四、为什么这个错误会反复发生

问题不是某一次 Schema 写错，而是编码决策顺序错误。

错误顺序是：

```text
先设计类型和 Schema
→ 再要求 AI 完全适配 Schema
→ 模型出现未预料表达
→ 继续增加规则和枚举
→ 系统越来越脆弱
```

正确顺序应该是：

```text
先判断程序掌握哪些确定事实
→ 判断哪些内容只能由 AI 或用户理解
→ 只冻结最小稳定协议
→ 为未知内容保留扩展空间
→ 最后才设计 Schema
```

本次错误反映出一个需要长期警惕的倾向：过度追求类型安全、确定性和“全覆盖”，却没有先验证这些信息是否真的可由程序知道。

## 五、正确做法

### 1. 只固定最小稳定外壳

AI 输出协议只固定程序继续执行所必需的字段，例如：

```json
{
  "status": "ready",
  "assistantReply": "已整理需求",
  "result": {}
}
```

其他内容根据业务重要性设计为：

- 可选
- 有默认值
- 允许未知字段
- 允许后续版本扩展
- 可以独立失败

### 2. 区分三种校验

#### 确定性技术校验

由程序严格执行：

- JSON 是否可解析
- 核心路由字段是否存在
- ID、权限、任务血缘是否正确
- 状态转换是否合法
- 文件和供应商技术限制是否满足

#### 格式规范化

由容错解析器或格式修复模型执行：

- 缺少非核心字段时补默认值
- 忽略或保留未知字段
- 兼容常见字段别名
- 修复明显的层级错位
- 只修格式，不改变用户语义

#### 业务语义判断

交给对应责任主体：

- 需求是否充分：需求 AI 判断，不足则询问用户
- 主体修改是否获得授权：需求 AI 根据用户原话判断
- 生成图是否保持主体：质检 AI 对比原商品图、生成图和用户需求
- 最终是否停止：程序根据 AI 的结构化结论和既定流程状态决定

### 3. 核心结果和辅助结果解耦

推荐处理顺序：

```text
先取得最终需求
→ 最终需求可用则允许主流程继续
→ 图片记忆成功则保存
→ 图片记忆失败则记录告警并延后补充
```

不得因为以下情况阻断需求整理：

- `creativeFacts` 缺失
- OCR 为空
- 图片记忆增加了未知字段
- 非核心说明文字格式不同

### 4. 开放字段采用开放数据结构

以下内容不能使用无法扩展的封闭枚举：

- 商品特征
- 差异类型
- 图片事实
- 创意事实
- 新供应商返回的扩展信息

应保留：

- 稳定的顶层分类
- 开放的具体 Key
- 原始模型观察
- 未识别扩展字段

### 5. 页面设置和程序事实不要交给 AI 决定

图片数量、比例、模型 ID、项目 ID、资产 ID等程序已经知道的事实，不需要让 AI 重新生成后再进行语义校验。

正确方式是：

```text
程序事实由程序直接写入最终任务
AI 只负责理解和整理开放语义
```

这样可以减少模型输出字段数量，也可以避免模型偶然改动确定性设置。

### 6. 格式错误不得直接等同于业务失败

正确流程：

```text
模型原始输出
→ 最小外壳解析
→ 容错规范化
→ 必要时进行一次仅格式修复
→ 再次解析
→ 核心字段仍不可用才停止
```

格式修复输入必须包含：

- 原始模型输出
- 具体格式错误
- 目标最小协议
- “不得改变用户原意，只能修复 JSON 结构”的明确限制

格式修复不计入业务重试次数。

### 7. 错误必须保留真实阶段和原因

禁止把所有异常压缩为 `Bad Gateway Exception`。

至少应区分：

```text
UPSTREAM_NETWORK_FAILED
UPSTREAM_REJECTED_REQUEST
AI_OUTPUT_NOT_JSON
AI_OUTPUT_ENVELOPE_INVALID
AI_OUTPUT_NORMALIZATION_FAILED
CORE_REQUIREMENT_MISSING
```

日志和数据库需要保存内部诊断原因；前端显示经过整理的用户提示，不能让内部信息丢失。

## 六、以后写代码时必须执行的检查清单

在为任何 AI 输出新增 Schema、枚举或程序规则前，必须回答：

1. 这个信息是程序确定知道的，还是只能由 AI/用户理解？
2. 如果未来出现当前没想到的值，系统应该失败还是保留？
3. 这个字段缺失是否真的应该阻断核心任务？
4. 这是业务错误，还是仅仅格式不同？
5. 能否由程序直接提供该值，而不是让模型重复生成？
6. 是否把辅助产物错误地设成了核心成功条件？
7. Schema 是否使用了不必要的 `.strict()` 或封闭枚举？
8. 是否存在默认值、未知字段保留和向前兼容策略？
9. 是否有一次只修格式、不改变语义的修复机会？
10. 失败时能否看到真实阶段和原始原因，而不是统一 500/502？

任何一个问题无法明确回答，都不能直接增加严格业务校验。

## 七、必须长期遵守的工程原则

### 原则一

> 程序只严格校验它真正掌握的确定性事实，不假装理解开放业务语义。

### 原则二

> AI 输出协议采用“最小稳定外壳 + 开放业务内容”，未知不等于非法。

### 原则三

> 格式失败、辅助能力失败和业务失败必须分开处理。

### 原则四

> 不得为了类型完整而牺牲真实可用性，不得让非核心字段阻断核心流程。

### 原则五

> 在增加校验前先证明程序有能力判断；无法证明时，应采用 AI 判断、用户澄清、容错保存或后置质检。

## 八、本次应吸收的结论

这次不是模型不能理解图片，也不是模型名称配置错误。模型已经返回了可用语义，系统失败是因为程序把自己未预料到的表达方式认定为非法。

真正需要修正的不是继续补更多枚举和必填字段，而是重新划分责任边界：

```text
程序负责确定性
需求 AI 负责语义理解
质检 AI 负责视觉一致性判断
用户负责最终意图和必要澄清
容错层负责格式差异
```

后续所有 AI 模块设计和代码评审，都必须先阅读并遵守本文件。
